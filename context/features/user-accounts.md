# Облікові записи та обране

## Поведінка

Реєстрація і вхід на `/login` працюють через ASP.NET Core Identity та локальну PostgreSQL. Демонстраційного обходу `admin` / `12345` немає; початкові акаунти не створюються. Спортивні сторінки залишаються публічними. `/profile` доступна після входу, посилання на неї є у верхній панелі.

Реєстрація приймає унікальні логін (3–30 латинських літер, цифр, `_`, `-`), пошту до 254 символів, пароль 12–128 символів та поточні мову/тему. Пробіли в паролі зберігаються; вимог до обов’язкових спеціальних символів немає. Унікальність логіна й пошти регістронезалежна та підкріплена індексами БД. Успішна реєстрація одразу відкриває профіль. При вході використовується логін.

У профілі показуються логін, пошта, налаштування та до 20 обраних пілотів і 20 команд. Варіанти беруться з поточного заліку; раніше збережені учасники залишаються доступними за своїми назвами, навіть якщо їх немає у поточному сезоні. Відомі ID перевіряються через спортивні довідники БД. Обране зберігається кнопкою та має посилання на спортивні профілі. Обране не є копією очок конкретного сезону. Персональна головна сторінка — наступний етап.

Мова і тема застосовуються з акаунта після входу/відновлення сесії. Зміни будь-якого перемикача автоматично записуються з паузою 400 мс; запити запису послідовні, а запізнілий запис попереднього користувача не застосовується до наступного. Помилка збереження видима. Незбережений вибір обраного не скидається при збереженні теми/мови. Гості продовжують використовувати локальні налаштування. Клієнтські секрети і сесійні токени у `localStorage` не записуються.

## API та захист

| Метод і адреса | Призначення |
| --- | --- |
| `GET /api/auth/csrf` | Отримати identity-bound request token у `XSRF-TOKEN` |
| `POST /api/auth/register` | `{login, email, password, language, theme}`; створити користувача й cookie |
| `POST /api/auth/login` | `{login, password}`; відкрити сесію |
| `GET /api/auth/me` | Приватний DTO профілю; без сесії 401 |
| `POST /api/auth/logout` | Завершити браузерну сесію через Identity |
| `PUT /api/auth/preferences` | `{language, theme}` лише для поточного користувача |
| `PUT /api/auth/favourites` | `{driverIds, teamIds}`; атомарна заміна його обраного |

Відповідь містить лише ID, логін, пошту, налаштування, обрані ID та їхні назви. Паролі, хеші, security stamp і службові поля не повертаються. `UserId` не приймається від клієнта: акаунт визначається за автентифікованою сесією. Незнайомий користувач і неправильний пароль мають однакову безпечну відповідь; неуспішна реєстрація не розкриває, яке саме поле вже зайняте.

Паролі хешує Identity v3/PBKDF2 зі 210 000 ітерацій. П’ять невдалих перевірок блокують вхід на 10 хвилин; 20 запитів входу/реєстрації на хвилину з одного IP обмежуються стандартним rate limiter. Ліміт діє в межах процесу; у dev-proxy всі користувачі мають спільну loopback-адресу. Розмір тіла auth-запиту обмежено 16 КіБ.

Сесія — захищена Data Protection cookie `F1RaceLens.Session`, HttpOnly, SameSite=Strict, вікно 8 годин зі sliding expiration. Вона не є persistent cookie: тривалість браузерної сесії також залежить від браузера. У production cookie вимагає HTTPS; HTTP дозволено лише в Development. Вихід видаляє cookie цього браузера; це не механізм відкликання скопійованого квитка або всіх пристроїв. Для майбутніх керованих пристроїв/негайного відкликання потрібен окремий реєстр сесій.

Кожна зміна, включно зі входом, реєстрацією та виходом, перевіряє ASP.NET Core antiforgery token у `X-XSRF-TOKEN`. Angular отримує новий token перед кожним записом, зокрема після зміни ідентичності. Приватні відповіді не кешуються. Frontend і API використовують один origin через dev-proxy, CORS для сторонніх доменів не відкривається.

Ключі cookie зберігаються в `.local/identity-keys`, на Windows зашифровані DPAPI поточного користувача; після перезапуску API сесія відновлюється. Файли ключів, локальні налаштування і дампи виключені з Git. Для іншого production-хоста слід налаштувати захищене сховище ключів/ACL, HTTPS і довірений reverse proxy; у цій задачі публічне розгортання не виконувалося.

## Зберігання і залежності

`RaceLensDbContext` розширює `IdentityUserContext<ApplicationUser>`. Міграція `UserAccounts` додає `AspNetUsers`, `AspNetUserClaims`, `AspNetUserLogins`, `AspNetUserTokens` та `UserFavourite`; спортивні таблиці й зафіксовані прогнози не змінюються. Міграція застосовується стандартною командою `--migrate` після backup. У pgAdmin ці таблиці розміщені в `public` поряд зі спортивними; хеші паролів не копіювати у повідомлення або скриншоти.

Додано офіційні пакети Microsoft `Microsoft.AspNetCore.Identity.EntityFrameworkCore` і тестовий `Microsoft.AspNetCore.Mvc.Testing` 10.0.4. [Документація Identity](https://learn.microsoft.com/aspnet/core/security/authentication/customize-identity-model?view=aspnetcore-10.0), [antiforgery](https://learn.microsoft.com/aspnet/core/security/anti-request-forgery?view=aspnetcore-10.0). Засіб доступності [axe-core від Deque](https://github.com/dequelabs/axe-core) — лише devDependency, без виконання у production. Платні сервіси, поштові API й зовнішні постачальники входу не підключені.

## Перевірки та межі

- 109 backend-тестів, включно з п’ятьма новими HTTP-сценаріями у тимчасових схемах PostgreSQL: реєстрація/хеш/відновлення/вихід, CSRF, ізоляція й обране, дублікати/lockout, rate limit/розмір запиту. Схеми видаляються після тестів, секрети не друкуються.
- 123 frontend-тест: реальні HTTP-контракти форм, збереження/відновлення, відсутність токенів у сховищі, guard, недоступний logout, CSRF, обране й незбережений вибір під час автозбереження налаштувань, збій каталогу мови та недоступні спортивні списки.
- `check:i18n`: 773 повідомлення в усіх каталогах; production build без попереджень. Три перевірки axe (вхід, реєстрація, профіль) проходять у jsdom; правило контрасту вимкнене через відсутність layout у jsdom, повного браузерного axe-аудиту це не замінює.
- Живий цикл: тимчасовий QA-акаунт, вхід через frontend proxy, збереження Antonelli/Mercedes, шість мов, світла/темна теми, вихід, зміна гостьових налаштувань і повторний вхід з відновленням французької/світлої теми з БД. Після перезапуску API й reload cookie, мова, тема й обране збереглися. На 320 px виправлено накладання кнопок профілю/виходу; горизонтального переповнення немає. QA-акаунт і його приватний файл видалено після перевірки; залишилися всі 1495 спортивних результатів і 12 зафіксованих прогнозів.

Підтвердження пошти, відновлення/зміна пароля, OAuth, MFA, платежі та персональна головна ще не реалізовані. `EmailConfirmed` залишається false; акаунти не позначаються як перевірені. Це готовий локальний етап, а не завершений публічний комерційний запуск.
