# Інтегровані прогнози та журнал точності

Рекомендований поточний запуск оновлення — [єдина локальна команда](forecast-update-workflow.md), яка оновлює дані та обидва рушії, публікує й оцінює прогнози. Окремі команди в цьому документі описують нижчий рівень інтеграції.

## Сторінка

`/predictions?engine=script` — контекстний статистичний скрипт, `/predictions?engine=ml` — збережений LightGBM v4. Вибір у URL підтримує прямі посилання та історію браузера. Є спільні режими підсумку сезону й майбутніх Гран-прі, цілі очки, версія, час розрахунку, час збереження та повідомлення про застарілі дані. Сценарії доступні лише для скрипта й не записуються як базові прогнози. Інтерфейс підтримує шість мов.

«Перевірка точності» окремо завантажує журнал обох рушіїв. Рядки розділені за етапом, версією і cutoff; віддалений прогноз після етапу 17 не прирівнюється до прогнозу після етапу 22. Відсотки поки не визнані відкаліброваними. Перевірка гонок не доводить точності шансів на чемпіонство.

## API та ML

- `GET /api/predictions/current` — скрипт і збереження свіжого базового розрахунку.
- `POST /api/predictions/scenario` — ручний сценарій без запису в журнал.
- `GET /api/predictions/ml` — перевірений локальний звіт LightGBM v4 та збереження в БД.
- `GET /api/predictions/accuracy` — оцінювання за повними офіційними результатами, додавання нових оцінок і відповідь із поточними статусами.

ML не потребує процесу на 4300. Backend читає фіксований `reports/season-forecast-lightgbm-v4.json` з `Predictions:MlRoot` або за замовчуванням із `ml/` репозиторію. Шлях задає адміністратор, HTTP-клієнт не передає файлових шляхів чи команд. Навчання і симуляції не запускаються HTTP-запитом.

Перерахунок із директорії `ml`:

```powershell
.venv/Scripts/python.exe -m f1ml.cli forecast --model-version lightgbm-v4
```

Звіт тепер включає `input_snapshot`: точні календар/заліки, нормалізовані результати поточного сезону та metadata моделі, які використовував цей розрахунок. Backend перевіряє чотири SHA-256 ваг/схем, metadata, поточний сезон, часові мітки, cutoff, склад майбутнього календаря та розподіл шансів перемоги. Ризик ML у шкалі 0–1 переводиться в 0–100 для спільного DTO. Якщо відбувся етап, а ML ще не перерахована, повертається `synchronizing` без минулих прогнозів. Відсутній/пошкоджений артефакт повертає 503, не підміняється скриптом. Збій ML не заважає вибрати скрипт.

Старі звіти без `input_snapshot` треба перегенерувати. Ваги й середовище не публікуються в Git. q1 та старий файловий журнал залишаються окремими експериментами; імпорту їхніх дат заднім числом немає.

## PostgreSQL

- `ForecastRuns`: незмінні входи/виходи, SHA-256, engine/version, сезон/cutoff, час генерації, джерела та першого запису. Скрипт зберігає також seed, історію трас, календар/заліки та агреговану погоду; ML — metadata, seed і контрольні суми ваг.
- `ForecastSeals`: перша фіксація до відомого UTC-старту, окрема для engine/version/season/round/cutoff. Час фіксації береться із серверного годинника під час першого запису в БД, не з дати старого файлу. Повторні/уточнені розрахунки не замінюють першу фіксацію.
- `ForecastScores`: оцінки й повні нормалізовані результати, що використовувалися для них; нова офіційна ревізія додає запис, не перезаписує стару оцінку.

Публікація атомарна, advisory lock і унікальні індекси захищають повторні паралельні запити. Застарілі відповіді, ручні сценарії та неготові прогнози не публікуються. Пізній розрахунок може зберігатися як run, але не отримує фіксації для вже розпочатої гонки. За невідомого часу старту фіксації немає. Збережений run сам по собі не означає придатності до оцінювання кожної гонки.

Прогнозні JSON зберігаються як TEXT, щоб хеш відтворювався з точного збереженого тексту. Міграція `ExactForecastPayloads` переводить перші локальні записи з JSONB у TEXT і одноразово перераховує їхні хеші, зберігаючи вміст та дати фіксацій. Перед оцінюванням перевіряються хеші входів і виходів. Це локальна перевірка цілісності, не зовнішнє засвідчення часу чи захист від адміністратора БД.

## Оцінювання

До старту статус `pending`. Після старту використовуються лише свіжі повні результати з однаковим набором пілотів та однозначними позиціями 1…N. Неповна класифікація чи зміна складу не оцінюється на частковій вибірці. Відсутні результати дають `awaiting-results`, розбіжність складу/класифікації — `roster-mismatch`.

MAE — середній модуль різниці між фактичною позицією і місцем у прогнозному порядку за очікуваними очками (потім середнім місцем та ID). Brier — сума `(p_i − y_i)²` для всього розподілу переможця, без ділення на кількість пілотів. Влучання переможця — чи виграв фаворит за найбільшим шансом; рівні шанси розв'язуються за ID. Менші MAE/Brier кращі.

На контрольному зрізі 19.10.2026 є 12 фіксацій (по 6 від кожного рушія) після етапу 17, оцінених майбутніх гонок — 0. Оцінювання відбувається при відкритті/оновленні журналу, не за фоновим розкладом. Загальна частота влучань, калібрування титулу, q1 і автоматичне оновлення/навчання — наступні розширення.
