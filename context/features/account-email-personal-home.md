# Пошта акаунта та персональна головна

## Gmail SMTP

Локально налаштовано Gmail SMTP (`smtp.gmail.com:587`, STARTTLS). Користувач сам ввів пароль застосунку через `scripts/accounts/Setup-Gmail.ps1` і погодив тестовий лист на власну адресу; за показаним результатом Gmail прийняв лист. Це не перевірка розміщення листа у папці «Вхідні». API перезапущений із новими налаштуваннями. Секрет і адресу не включати у Git, журнали, тести чи документацію.

Повторне налаштування: `pwsh -File ./scripts/accounts/Setup-Gmail.ps1`. Для Google потрібні двоетапна перевірка і окремий пароль застосунку. Основний пароль Google не використовується. Скрипт приховує введення, обмежує ACL приватного конфігу поточним користувачем і SYSTEM, зберігає інші ключі, зокрема БД, і лише за локальним `y` надсилає один тестовий лист на адресу відправника. SMTP-пароль зберігається в приватному локальному конфігу відкритим для власника процесу; це не сховище секретів для публічного хоста. [Google: паролі застосунків](https://support.google.com/mail/answer/185833?hl=en), [Gmail SMTP](https://support.google.com/mail/answer/7104828?hl=en).

Історичний префікс конфігурації `PasswordRecovery:*` тепер спільний для відновлення пароля, підтвердження та зміни пошти. Транспорт ін’єктується через `IAccountMailTransport`; backend-тести замінюють чергу/транспорт і не звертаються до реального Gmail. Листи перекладені шістьма мовами за мовою акаунта. SMTP TLS/перевірка сертифіката обов’язкові. Origin задається фіксовано, без Host користувацького запиту. Для Development дозволено HTTP лише на loopback; у Production потрібен HTTPS origin. Поточний `127.0.0.1:4200` призначений для користувача цього самого комп’ютера, не для віддалених відвідувачів.

Черга обмежена 64 записами, у пам’яті процесу, без автоматичних повторів і гарантії доставки після перезапуску. 202 означає прийняття запиту, а не доставку. Помилки надсилання логуються загальним повідомленням без винятку/адреси/токена. Gmail має власні обмеження й політики; для комерційного розгортання потрібні домен, HTTPS, контроль доставки та відповідний поштовий провайдер. Платні підписки не оформлялися.

## Підтвердження й зміна пошти

У DTO профілю додано `emailConfirmed`. Identity вже має це поле: нова міграція не потрібна. Підтвердження не увімкнено як обов’язкову умову входу, щоб не заблокувати вже створені акаунти.

| Endpoint | Поведінка |
| --- | --- |
| `POST /api/auth/request-email-confirmation` | Тільки поточний акаунт; підтверджений — 204, прийнятий до черги — 202, недоступна доставка — 503 |
| `POST /api/auth/request-email-change {newEmail,currentPassword}` | Поточна сесія, перевірка пароля з lockout; стара адреса ще не змінюється |
| `POST /api/auth/confirm-email {userId,token}` | Підтвердити адресу через Identity; неправильний/прострочений/використаний токен — однакова 400 |
| `POST /api/auth/confirm-email-change {userId,token,newEmail}` | Змінити й підтвердити адресу, відкликати сесії; логін і пароль залишаються тими самими |

Усі записи захищено CSRF, включно з гостьовим підтвердженням. Запити надсилання ділять ліміт відновлення — 5/15 хвилин/IP; застосування токенів — account-entry 20/хвилину/IP. Невдале введення поточного пароля враховується у lockout 5/10 хвилин. Адреса перевіряється й має не більше 254 символів. Відповідь запиту зміни на зайняту адресу теж 202, без надсилання листа іншому власнику: наявність чужого акаунта не розкривається. При підтвердженні унікальність перевіряється Identity та індексом БД, включно з race condition.

При реєстрації лист підтвердження ставиться у чергу, якщо доставка налаштована; без доставки можна повторити з профілю. Помилка/переповнення черги не означає втрату створеного акаунта; статус у профілі лишається непідтвердженим.

Токени Identity Data Protection живуть 30 хвилин від створення, прив’язані до користувача, stamp, призначення, а для зміни — також до точної нової адреси. Підтверджений email не підтверджується повторно; успішна зміна адреси оновлює stamp і робить попередні посилання недійсними. Посилання `/confirm-email#user=…&token=…` та `/confirm-email-change#user=…&token=…&email=…` передають секрет у fragment, який форма прибирає з поточної адреси. Token не зберігається у localStorage і надсилається лише у тілі POST. GET сам нічого не змінює: потрібне явне натискання «Підтвердити», щоб перегляд посилання поштовим сканером не змінював акаунт.

Нова адреса набирає чинності лише після підтвердження. Поточна cookie видаляється, інші стають недійсними на наступному автентифікованому запиті. Вхід повторюється з попереднім логіном. Персональні налаштування, обране й ID користувача зберігаються.

## Персональна головна

Після входу під каруселлю з’являється блок обраного, прив’язаний до `AuthService.user()`; для гостя він не займає місця і не виконує запитів. Порожнє обране веде у профіль. Пілоти й команди мають очки, місце та перемоги з наявних ресурсів головної поточного сезону. Інший рік не підмішується. Архівний/відсутній у заліку учасник не зникає з обраного: показується його назва й пошук, замість неправильного поточного профілю.

Для всього обраного виконується лише один додатковий запит результатів гонки останнього етапу, підтвердженого заліком пілотів того ж сезону й календарем. Для пілота зберігаються класифікаційне місце, статус (включно зі сходом) та очки; класифікація не видається за фактичний фініш. Для команди підсумовуються очки лише за цю гонку, без спринту, за точним збігом назви з поточним джерелом: поточний контракт результатів не має ID конструктора. Без надійного збігу чи з пропусками очок — рисочка, не вигаданий нуль. За зміни акаунта старе обране ховається одразу.

Наступний етап і час беруться з існуючого календаря; особисту участь кожного обраного учасника це не підтверджує. Для минулого старту без оновленого заліку є позначення очікування результатів. Помилка результатів не ховає заліки, доступна окрема повторна спроба; дати/застарілість джерел видимі. Симуляції, ML, нові таблиці БД й індивідуальні запити на кожного пілота не додаються.

## Перевірки

HTTP/PG-тести у тимчасових схемах перевіряють явність підтвердження, CSRF, неправильного користувача/призначення/нову адресу/повторне використання, строк дії, дублікати, збереження старої адреси, відкликання сесій і незмінний логін. Окремий worker-тест генерує всі три типи локалізованих листів із транспортом у пам’яті. Жодних справжніх листів із тестовими акаунтами не надсилається. Frontend-тести перевіряють відсутність автоматичного застосування посилань, валідацію, очищення пароля, чесні помилки SMTP, гостя/порожнє/архівне обране, різні роки, збій результатів, повторну спробу, зміну акаунта та axe структуру форм/карток. Реальна авторизована зміна пошти користувача під час QA не виконується.

Результат: 139 backend-тестів без пропусків, 147 frontend-тестів, обидві збірки без попереджень, 929 повідомлень локалізації. Окремо перевірені дозволений HTTP loopback у Development і заборонені зовнішні HTTP-hostnames/Production HTTP. Живі гостьова головна, українська/німецька сторінка підтвердження і ширина 320 px без горизонтального переповнення. Авторизовані сценарії перевірено в ізольованих HTTP/PG та компонентних тестах; особистий акаунт користувача не змінювався. API й frontend залишені запущеними, storage health — ready. Без коміту.
