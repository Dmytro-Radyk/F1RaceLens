# Єдина команда оновлення прогнозів

З кореня репозиторію, PowerShell:

```powershell
./scripts/Update-Forecasts.ps1
```

Потрібні налаштована PostgreSQL, виконані міграції, ML-середовище з вагами LightGBM v4 та Debug-збірка API (`dotnet build backend/F1RaceLens.slnx`). Команда запускає локальну БД за потреби. API/frontend можуть працювати під час оновлення, але для самої команди HTTP-сервер не потрібний. Автоматичне встановлення залежностей, перенавчання й розклад не запускаються.

## Етапи

Під OS-lock етап `preflight` перевіряє локальні залежності та запускає `scripts/database/Start.ps1`; збій БД теж записується як невдала спроба. Далі виконуються три робочі етапи:

1. `data`: окремий процес API `--refresh-data` завантажує свіжий календар/заліки поточного сезону й результати двох останніх підтверджених етапів: гонок, кваліфікацій та доступних спринтів. Старіші непорожні результати використовує з PostgreSQL, відсутні — дозавантажує. Зберігає спортивні DTO-зрізи, сирі документи й проєкції. Профілі пілотів та архів усіх сезонів не перевантажуються. Пізні виправлення старих гонок поза цим вікном не імпортуються масово; журнал точності окремо запитує актуальні результати зафіксованих гонок.
2. `ml`: Python `forecast --model-version lightgbm-v4 --refresh-current` оновлює результати 2026 та pinned календар/заліки, розраховує новий прогноз на наявних вагах. Готовий звіт та вхідний зріз публікуються через атомарну заміну файлу.
3. `publish`: окремий процес API `--publish-forecasts` обчислює свіжий скрипт, перевіряє ML та зіставляє сезон, cutoff, календар, вихідні очки/місця й активний склад. Обидва базові розрахунки записуються в журнал, чинні фіксації не змінюються. Журнал оцінює вже завершені гонки.

CLI-процеси мають власні порожні кеші й не відкривають HTTP-порт. Оркестратор запускає скомпільований API DLL без `dotnet run`, щоб таймаут завершував саме робочий процес. API-завдання має cancellation timeout 14 хвилин, зовнішній процес — 15 хвилин на етап.

CLI-запити Jolpica мають спільну чергу з інтервалом 600 мс і максимум чотири спроби для GET при 429/503. `Retry-After` у секундах або HTTP-date не скорочується; cooldown понад дві хвилини завершує спробу, а не породжує ранні повтори. Python теж підтримує обидві форми заголовка. Код процесу 3 дає публічну причину `source-busy`, не текст винятку. [Ліміти джерела](https://github.com/jolpica/jolpica-f1/blob/main/docs/rate_limits.md) спільні для IP, тому сервер може відмовити навіть за коректного локального обмеження.

Запущений HTTP API підхоплює свіжий опублікований скрипт із БД без перезапуску. Пріоритет — найбільший cutoff, потім свіжіший вхідний зріз і час розрахунку. Вік кешу не продовжується кожним читанням: свіжість обмежена 15 хвилинами від генерації. Сценарії відновлюють `ForecastInput` саме з цього run; опубліковані сценарії не підмішуються в базовий журнал. ML читає атомарно замінений файл; його Windows file handle дозволяє rename/delete під час читання.

## Стан і збої

`GET /api/predictions/update-status` — лише читання. На `/predictions` кнопка «Оновлення даних» відкриває панель стану та останнього успішного запуску. «Перевірити оновлення» в цій панелі перечитує стан, не запускає розрахунок. Підтримані шість мов; polling немає.

Локальні файли поза Git:

- `.local/forecast-update.json` — атомарний стан поточної/останньої спроби та `lastSuccessfulAt`;
- `.local/forecast-update.lock` — OS-lock одного циклу; зайнятий lock дає exit 2 без зміни чужого стану, при завершенні процесу ОС звільняє блокування;
- `.local/update-logs/<run>-<stage>.log` — окремий журнал кожного підпроцесу.

Публічний DTO містить лише дозволені стани/етапи, дати й загальний код помилки. Шляхи, stdout/винятки, PID, рядок підключення та паролі не повертаються. Пошкоджений стан дає `unavailable`; `running` без оновлення понад годину — `interrupted`. Відсутній файл — `never`.

Після помилки наступні етапи не виконуються; попередній час успіху зберігається. Раніше опубліковані прогнози й фіксації не видаляються. Немає єдиної транзакції між мережею, файлами й усією БД: уже успішно імпортовані спортивні ресурси або готовий ML-файл можуть залишитися після збою наступного етапу. Повторний запуск безпечний щодо існуючих фіксацій. Не запускати паралельно ручне навчання/перезапис ваг; OS-lock охоплює тільки цю команду.

Правила прогнозу перевірені для сезону 2026; у новому році цикл зупиниться до явного оновлення правил. Точність і сила моделі від додавання оркестратора не змінюються.
