# Що зберігати у майбутній PostgreSQL

Це план наступного етапу, не поточна реалізація бази. Зараз API має лише кеш у пам’яті. Профіль пілота додав вимоги, які слід врахувати перед створенням міграцій.

| Сутність | Дані та важливі зв’язки |
| --- | --- |
| Пілот | Стабільний `driverId` джерела, ім’я, код, дата народження, громадянство; відсутні значення — NULL |
| Команда | Стабільний `constructorId`, назва й історичні назви у знімках сезону |
| Сезон і участь | Рік; зв’язок пілот–сезон–команда є множинним, оскільки можливі трансфери |
| Траса і Гран-прі | `circuitId`, назва й місце; етап визначається сезоном і номером, дата та траса належать конкретному проведенню |
| Сесія | Гонка, кваліфікація, спринт тощо; дата окремо від nullable UTC-часу початку |
| Запис результату | Пілот, команда саме на цьому етапі, стартовий номер/автомобіль із сирого джерела, місце, positionText, статус, старт, кола, час/відставання, decimal-очки; Q1/Q2/Q3 для кваліфікації |
| Знімок заліку | Сезон, етап, вид заліку, час імпорту; авторитетні очки, перемоги, nullable місце й ознака виключення для кожного учасника |
| Імпорт джерела | URL запиту без секретів, UTC-час отримання, версія адаптера, хеш і сирий JSON; дозволяє перевірити та повторно нормалізувати дані |

## Правила, які не можна загубити

- Не робити пару «пілот–сезон» єдиним зв’язком команди: команда змінюється протягом року. Не брати команду всіх минулих гонок із поточного профілю.
- Не ставити унікальність лише на «пілот–сесія»: в історії один пілот може мати кілька записів одного етапу. Потрібен окремий ідентифікатор запису; перед визначенням природного ключа зберігати номер автомобіля та сирий запис. Публічний DTO профілю зараз не містить усіх полів для такого ключа, тому його недостатньо для безвтратного імпорту.
- Місце класифікації та фактичний фініш — різні речі. Не замінювати сходи останнім місцем, а відсутні дані — нулем.
- Очки зберігати як `numeric/decimal`, зі знаком. Не виводити чемпіонський залік лише із суми гонок: є спринти, виключення, штрафи та правила відкидання результатів.
- Не підміняти історичний стартовий номер поточним постійним номером довідника.
- Історичні дані можуть виправлятися. Повторний імпорт має оновлювати записи ідемпотентно; повну нову версію знімка заліку/сесії записувати транзакційно після всіх сторінок, без часткових таблиць.
- Зберігати `fetchedAt` і походження; не називати час отримання часом оновлення джерела. Політику свіжості визначати окремо для довідників, поточного сезону й архіву.
- Графік, середні показники й легенду не зберігати як первинні дані: вони відтворюються з результатів. Зберігати версію формули, лише якщо пізніше з’являться окремі обчислені рейтинги.

## Порядок впровадження

1. Підготувати PostgreSQL, EF Core, міграції, змінні середовища та резервне копіювання без секретів у Git.
2. Реалізувати сховище нормалізованих сутностей і сирих імпортів із вищенаведеними історичними випадками.
3. Перевести читання API на базу; зовнішній імпорт робити атомарно, зі збереженням придатної попередньої версії при помилці.
4. Імпортувати вибрані історичні сезони з обмеженням частоти запитів; окремо налаштувати оновлення поточного сезону.
5. Перевірити збереження після перезапуску, відновлення резервної копії, повторний імпорт без дублів та коректність shared-car результатів і дискваліфікацій.

Обрані пілоти, налаштування графіків і профіль користувача потребуватимуть окремих користувацьких таблиць, коли буде реалізована справжня авторизація. До поточної задачі вони не входять.
